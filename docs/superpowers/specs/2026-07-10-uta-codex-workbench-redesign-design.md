# UTA Codex 式通用 Agent 工作台改造设计

日期：2026-07-10

状态：设计讨论已确认，等待书面审阅

适用范围：UTA 桌面端产品体验、桌面桥接层，以及与对话任务相关的核心接口

## 1. 决策摘要

UTA 的产品方向从“展示 Agent 流程的可视化控制台”调整为“对话驱动的通用 Agent 工作台”。

最终采用以下核心决策：

- 产品定位采用“通用版 Codex”：交互方式接近 Codex，但任务范围不限于编程。
- 主界面采用“Codex 工作台”：聊天位于中央，当前任务信息位于可折叠右侧面板。
- 左侧采用“会话优先混合型”导航：上半区是新任务与最近会话，底部是知识库、记忆中心、技能与工具、设置与授权。
- 工作区为可选项：普通聊天无需绑定目录；需要访问本地文件时再选择并授权目录。
- 同一对话可同时包含普通聊天和多次任务，不提供“聊天模式/任务模式”开关。
- 每条用户消息都先由模型结合会话上下文判断意图，不再依赖写死的关键词路由。
- 读取、分析、检索等低风险操作默认直接执行；写入、删除、Shell、Python 等高风险操作在执行前逐次授权。
- 步骤清单、日志和 state 不再进入最终回答，只在右侧任务面板和诊断入口展示。
- 只有真实工具返回成功并完成结果核验后，Agent 才能声明任务完成。

## 2. 背景与问题

当前 UTA 已经具备对话、任务规划、工具执行、checkpoint、长期记忆、RAG 知识库、技能包和桌面端打包能力。主要问题不在底层能力不足，而在产品结构仍然围绕“流程可视化控制台”设计：

- 用户首先看到步骤、日志、state 和状态面板，而不是自然对话。
- 普通聊天和执行任务之间存在割裂，部分场景依赖关键词判断。
- 任务执行期间缺少连续反馈，用户容易只看到长时间等待和最后一次性输出。
- 会话历史、任务历史、短期记忆和长期记忆存在概念重叠。
- 知识库、记忆、技能等页面以数据堆叠为主，缺少清晰的用户操作目标。
- Agent 可能在工具未运行或操作未发生时，用语言生成“已完成”的假象。
- 前端逻辑集中在单个大型 `app.js` 中，继续增加功能会放大交互和布局问题。

本次改造保留有价值的 Agent 核心，将流程、日志和内部状态降级为诊断信息，把对话、任务结果、文件变化和授权确认提升为主要体验。

## 3. 产品目标

### 3.1 主要目标

1. 用户进入应用后可以像使用 Codex 一样直接开始对话或安排任务。
2. 普通聊天自然回复，执行型任务自动进入工具编排，不要求用户选择模式。
3. 任务执行过程持续可见，但不干扰阅读最终回答。
4. 文件、知识、记忆、技能和权限围绕对话任务组织，而不是作为独立的数据展示台。
5. Agent 的完成声明必须有工具结果、文件变化、来源或测试结果等证据。
6. 现有会话、记忆、知识库和配置数据可以继续使用。

### 3.2 非目标

- 不把 UTA 限定为代码 Agent。
- 不实现远程控制整台电脑。
- 不在首轮改造中实现多人协作、云同步或移动端。
- 不在主界面持续展示完整思维过程、原始 Prompt 或全部内部日志。
- 不在首轮改造中建设技能市场或插件商店。
- 不更换现有 pywebview + Python 的桌面进程架构。

## 4. 体验原则

### 4.1 对话是主界面

用户消息和 Agent 回复始终占据视觉中心。计划、工具调用和日志属于任务详情，不得挤压或替代对话。

### 4.2 先执行，再解释

低风险任务被识别后直接开始。Agent 不应只回复“我会做什么”，而应立即进入可观察的执行状态。

### 4.3 状态必须有意义

界面显示“正在读取文件”“正在搜索来源”“正在运行测试”等用户可理解的状态，不显示无意义的内部事件名。

### 4.4 授权发生在动作之前

高风险操作在真正执行前暂停并请求授权。授权弹窗必须说明目标、范围、风险和预期变化。

### 4.5 回答与证据绑定

最终回复只总结完成情况、结果和限制；文件、测试、来源、变更等证据以可点击项目展示。

## 5. 信息架构

### 5.1 左侧导航

左侧导航采用“会话优先混合型”：

- 顶部：UTA 品牌、新任务按钮、会话搜索。
- 主区：按时间分组的最近会话。
- 底部：知识库、记忆中心、技能与工具、设置与授权。

“会话历史”不再是独立页面。选择历史会话即回到对应的对话工作台。

### 5.2 对话工作台

中央区域包括：

- 对话标题。
- 当前工作区选择器；未绑定时显示“无工作区”。
- 消息流。
- 附件和引用资料。
- 底部输入框、发送按钮、停止按钮。
- 任务结束后的产物摘要和证据入口。

输入框固定在底部，不随执行状态改变位置。消息发送后立即进入消息流。

### 5.3 右侧任务面板

右侧面板只在当前对话存在执行任务时自动展开，用户可以随时收起。面板包含四个一级标签：

1. 进度：当前目标、步骤状态、等待授权、失败原因和重试入口。
2. 文件：当前工作区相关文件和本轮读取记录。
3. 变更：本轮新增、修改、删除内容及可恢复状态。
4. 产物：报告、表格、文档、代码修改、测试结果和其他交付内容。

原始日志、完整 state、内部事件和调试信息进入“诊断信息”二级入口，默认折叠。

### 5.4 知识库

知识库按资料集合组织，不再只展示一列文档：

- 创建和选择资料集合。
- 摄入文件或目录。
- 查看文档状态、更新时间、分块数量和失败原因。
- 在当前集合中检索或问答。
- 查看答案使用的来源片段。
- 将检索结果一键加入当前对话上下文。

### 5.5 记忆中心

记忆中心按语义和作用域分组：

- 当前会话摘要。
- 用户画像。
- 明确偏好。
- 工作习惯。
- 项目事实。
- 明确约束。
- 决策记录。
- 待确认内容。

每条长期记忆必须显示内容、来源会话、更新时间和置信状态，并支持编辑、删除和禁止继续使用。短期会话记忆与长期记忆不得混排。

### 5.6 技能与工具

该页面分为两个标签：

- 技能：名称、用途、来源、启用状态、命中条件和最近使用时间。
- 工具：能力说明、风险等级、所需权限、允许范围和最近调用结果。

技能负责“怎样完成一类任务”，工具负责“能够执行什么动作”，两者不得再混为同一列表。

### 5.7 设置与授权

设置页包含：

- 模型服务和连接测试。
- 联网搜索配置。
- 默认工作区和授权目录。
- 文件写入、文件删除、Shell、Python REPL 等高风险工具开关。
- 授权策略和最近授权记录。
- 本地数据存储位置。
- 会话压缩和记忆策略的高级配置。

## 6. 对话与任务流程

### 6.1 统一入口

所有用户输入进入同一个对话入口。系统将当前消息、当前会话摘要、最近消息、工作区状态和可用能力交给模型路由器。

模型路由器使用结构化输出返回：

- `conversation`：普通对话，直接生成模型回复。
- `quick_task`：一个或少量工具即可完成的任务。
- `complex_task`：需要计划、多个工具或验证步骤的任务。
- `clarification`：缺少关键参数，必须先向用户提问。

运行时不再以关键词命中作为正常路由方式。模型路由失败时允许重试一次；仍失败则明确请求用户澄清，不回退到伪造的固定答案。

### 6.2 普通对话

1. 用户消息立即显示。
2. Agent 回复占位进入“正在思考”状态。
3. 模型输出通过 `assistant_delta` 事件逐段显示。
4. 不创建任务面板，不写入任务历史。
5. 消息保存到当前会话并参与后续上下文。

### 6.3 执行任务

1. 用户消息立即显示。
2. 系统创建任务运行记录并发出 `task_started`。
3. 右侧任务面板展开。
4. 复杂任务生成内部计划，计划更新只进入右侧面板。
5. 工具执行过程持续发出用户可读状态。
6. 高风险操作发出授权请求并暂停对应步骤。
7. 工具返回后执行结果核验。
8. 通过核验后创建产物和证据，并生成最终回复。
9. 最终回复不得重复完整步骤清单或原始日志。

### 6.4 停止与继续

- 用户可以随时停止当前任务。
- 停止信号在 LLM 调用、工具调用和步骤边界处检查。
- 已完成步骤、工具结果、产物和 checkpoint 保留。
- 继续任务时从最近可恢复 checkpoint 开始，不重复已确认完成的步骤。
- 无法安全恢复的任务必须说明原因，并创建新的后续任务，不能假装续跑成功。

## 7. 后端模块边界

本次改造保留现有 `core/` Agent 能力和 pywebview 桥接方式，但重新划分桌面端职责。

### 7.1 ConversationService

职责：

- 创建、读取、搜索和归档会话。
- 保存消息、会话标题、当前工作区和会话摘要。
- 将一次会话中的多次任务关联到同一个 `conversation_id`。

### 7.2 IntentOrchestrator

职责：

- 组装模型路由上下文。
- 获取并校验结构化意图结果。
- 将普通对话交给回复生成器，将任务交给 TaskRuntime。

### 7.3 TaskRuntime

职责：

- 创建任务、执行计划、维护 state 和 checkpoint。
- 调用 Planner、Router、Executor、Verifier 和 Reflection/Replan。
- 处理停止、继续、失败和部分完成状态。

### 7.4 WorkspaceService

职责：

- 管理会话绑定的可选工作区。
- 校验授权目录和路径边界。
- 提供文件列表、读取记录和变更追踪。
- 为文件变更创建恢复信息。

### 7.5 PermissionService

职责：

- 对工具和动作进行风险分级。
- 判断是否允许自动执行、是否需要单次授权。
- 生成授权请求并记录用户决定。
- 阻止 Shell 命令通过路径参数绕过授权目录。

### 7.6 MemoryService

职责：

- 保存每个会话独立的短期摘要和最近消息。
- 提取并合并长期记忆候选。
- 保存来源、更新时间、类别和置信状态。
- 支持记忆编辑、删除、禁用和检索。

### 7.7 ArtifactService

职责：

- 统一登记任务产物。
- 验证文件、报告、来源和测试结果是否真实存在。
- 为最终回复和右侧面板提供可点击证据。

### 7.8 DesktopEventBus

职责：

- 将模型回复、任务状态、工具调用、授权请求、文件变化和产物统一推送给前端。
- 替代前端对大量零散事件和状态字段的特殊判断。

## 8. 统一事件协议

所有桌面事件采用统一信封：

```json
{
  "version": 1,
  "event_id": "唯一事件 ID",
  "conversation_id": "会话 ID",
  "task_id": "任务 ID，可为空",
  "type": "事件类型",
  "timestamp": "ISO 时间",
  "data": {}
}
```

首批事件类型：

- `assistant_started`
- `assistant_delta`
- `assistant_completed`
- `task_started`
- `plan_updated`
- `step_started`
- `step_completed`
- `step_failed`
- `tool_started`
- `tool_completed`
- `authorization_requested`
- `authorization_resolved`
- `file_changed`
- `artifact_created`
- `checkpoint_saved`
- `task_stopped`
- `task_completed`
- `task_failed`

前端只根据事件协议更新界面，不读取后端内部对象结构。

## 9. 数据模型与存储

默认数据继续存储在 `~/.uta/`。

建议结构：

```text
~/.uta/
  config.json
  conversations/
    <conversation_id>.json
  tasks/
    <task_id>.json
  checkpoints/
    <task_id>/
  artifacts/
    <task_id>/
  memory/
  knowledge/
  backups/
  trash/
```

### 9.1 会话与任务关系

- 一个会话包含多条消息。
- 一条用户消息可以不创建任务，也可以关联一个任务。
- 一个会话可以关联多次任务。
- 任务运行数据不复制到会话消息正文中，只保存引用和最终摘要。

### 9.2 工作区关系

- 会话可以没有工作区。
- 会话最多绑定一个当前工作区，但可以在新任务开始前切换。
- 切换工作区必须显式确认，历史任务仍保留原工作区引用。
- 授权目录与工作区分开保存：工作区是上下文，授权目录是安全边界。

### 9.3 会话压缩

- 每个会话独立维护最近消息、短期摘要和压缩位置。
- 压缩阈值根据模型上下文窗口动态计算，默认取上下文容量约 70%，并设置约 200k 到 300k token 的上限区间；小上下文模型采用更低阈值。
- 压缩保留用户目标、已确认约束、重要事实、未完成任务、文件与产物引用和最近消息。
- 稳定的用户画像、偏好、工作习惯、项目事实和决策记录作为长期记忆候选进入 MemoryService。
- 后续压缩以合并和补全为主，不重复堆叠相同记忆。

## 10. 权限与安全

### 10.1 风险等级

- 低风险：普通聊天、只读文件、知识库检索、网页搜索、数据分析，以及写入 UTA 自身的会话、checkpoint 和产物目录。
- 高风险：在用户工作区创建或修改文件、删除、覆盖、Shell、Python REPL，以及访问授权目录外路径。

高风险操作默认逐次授权。访问授权目录外路径的动作必须被拒绝，或要求用户先添加授权目录；仅打开“高风险工具”总开关不能扩大允许访问的目录范围。

### 10.2 路径安全

- 默认只允许 UTA 工作目录和用户明确授权的目录。
- 禁止访问系统敏感目录和应用内部资源目录。
- Shell 不得仅校验当前工作目录，还必须校验命令参数中的绝对路径、用户目录展开路径和重定向目标。
- 专用文件工具优先于通用 Shell 命令。

### 10.3 可恢复操作

- 删除移动到 UTA 回收站，不直接永久删除。
- 覆盖文件前保存备份或可恢复差异。
- 授权记录保存动作摘要，不保存 API Key 或敏感文件内容。

## 11. 完成真实性与错误处理

### 11.1 完成判定

Agent 只有满足以下条件才能声明完成：

1. 必要工具确实运行。
2. 工具返回成功状态。
3. Verifier 或 ArtifactService 对结果完成核验。
4. 所需文件、来源、测试或产物证据可被读取。

最终状态必须是 `completed`、`partially_completed`、`failed` 或 `stopped` 之一。

### 11.2 常见错误

- 模型路由失败：重试一次，仍失败则请求澄清。
- 模型输出中断：保留已生成内容，并提供重试入口。
- 工具不可用：明确说明缺少的能力或配置。
- 权限未开启：打开对应授权入口，不启动假任务。
- 授权被拒绝：将步骤标记为未执行，并重新评估后续计划。
- 网络错误：保留 checkpoint，恢复后继续。
- 文件验证失败：不得声明文件已创建或修改。
- 测试失败：最终状态不能显示全部完成。

## 12. 前端结构

现有单体 `desktop/frontend/app.js` 拆分为职责清晰的模块，建议结构：

```text
desktop/frontend/
  index.html
  styles/
    tokens.css
    shell.css
    conversation.css
    task-panel.css
    pages.css
  js/
    app.js
    api-client.js
    event-store.js
    router.js
    components/
    views/
      conversation.js
      knowledge.js
      memory.js
      capabilities.js
      settings.js
```

约束：

- `api-client.js` 只负责 pywebview 调用。
- `event-store.js` 只负责消费统一事件并更新前端状态。
- 各视图不得直接修改其他视图的 DOM。
- 对话输入框、任务面板和授权弹窗具有稳定尺寸，不因状态文字改变布局。
- Markdown 在渲染层转换为界面元素，不显示代码围栏或原始 Markdown 标记。
- 窄窗口下右侧面板改为覆盖抽屉，不能把对话区压到不可用。

## 13. 迁移策略

### 13.1 数据兼容

- 首次启动新版本时扫描旧 `~/.uta/conversations/`。
- 旧会话补充缺失的 schema 版本、工作区和任务引用字段。
- 旧任务历史转换为只读历史任务引用，不复制完整内容。
- 旧长期记忆保留，并在读取时映射到新的语义类别。
- 旧配置继续有效，新权限字段使用安全默认值。

### 13.2 回滚与备份

- 迁移前创建带时间戳的数据备份。
- 迁移过程写入新文件，校验成功后再替换索引。
- 迁移失败时继续使用旧数据并给出中文提示，不删除原数据。

## 14. 分阶段实施

本设计是总体架构规范。实施拆为五个可独立验收的阶段，每个阶段单独编写实施计划。

### 阶段一：新界面骨架

- Codex 工作台布局。
- 会话优先侧栏。
- 可折叠右侧任务面板。
- 新页面导航。
- 暂时兼容现有后端 API。

### 阶段二：新对话运行机制

- 模型结构化路由。

## 15. 测试与验收

### 15.1 自动化测试

- 模型路由结构校验和失败回退。
- 会话与多任务关联。
- 事件顺序、重复事件和断线恢复。
- checkpoint 停止与继续。
- 工作区和授权目录边界。
- Shell 路径参数绕过。
- 文件创建、修改、删除与恢复。
- 短期记忆隔离和长期记忆合并。
- 旧数据迁移和回滚。
- 前端各视图渲染和事件更新。

### 15.2 真实场景验收

1. 输入“你好”，由模型自然回复，不建立假任务。
2. 发送普通追问，模型能使用当前会话前文。
3. 发送复杂任务，右侧实时显示进度，最终生成真实产物。
4. 请求写文件，执行前弹出明确授权；拒绝后不声称完成。
5. 任务停止后从 checkpoint 继续，不重复已完成步骤。
6. 不同会话的短期记忆互相独立。
7. 长期记忆可以追溯、编辑、删除和禁用。
8. 知识库回答显示实际来源片段。
9. 旧会话、知识库和配置升级后仍可使用。
10. 全量测试、桌面端视觉检查、应用签名检查和压缩包完整性检查通过。

## 16. 成功标准

- 用户无需理解任务类型、Planner、Router、state 或 checkpoint 即可完成主要操作。
- 普通聊天与任务执行在同一对话中自然切换。
- 任务开始后持续出现有意义的状态反馈。
- 任何“已完成”都能找到对应证据。
- 主界面不再长期展示完整流程、原始日志或内部 state。
- 记忆、知识库、技能与工具各有清晰的页面职责。
- 现有用户数据升级后可继续使用。
- 五个实施阶段均通过对应自动化测试和桌面端真实场景验收。

## 17. 延后事项

以下能力不进入本轮改造：

- 多任务并行。
- 多人协作和云同步。
- 移动端。
- 语音交互。
- 自动控制整台电脑。
- 技能市场和在线插件安装。
- 永久后台自主运行。
