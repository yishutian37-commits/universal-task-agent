# 复杂任务拆解与 Checklist 执行设计

日期：2026-06-28

## 背景

UTA 当前已经有 `TaskParser -> Planner -> Agent Loop -> Router -> Executor -> Verifier` 的多步骤执行骨架，桌面端也能在“执行过程”里展示步骤，并在步骤完成后显示完成状态。但当前步骤主要来自固定任务模板或 Skill workflow，不能很好地处理用户输入中的复杂任务，也不会在最终结果里保留 `[ ]/[x]` 形式的执行清单。

本设计补齐复杂任务拆解和清单式进度展示，让用户看到任务从拆解到逐步完成的全过程。

## 目标

- 当用户输入复杂任务时，UTA 能识别为 `complex_task`。
- Planner 能根据自然语言任务拆分出 2 到 8 个可执行步骤。
- 桌面端执行过程使用 `[ ]`、`[...]`、`[x]`、`[!]` 显示待执行、执行中、完成和失败状态。
- 最终结果保留完整 checklist，完成步骤用 `[x]` 标记。
- 每一步仍走现有 Router/Executor/Verifier 链路，避免新增一套并行执行系统。

## 非目标

- 本次不做真正的任务并行执行。
- 本次不做用户手动编辑步骤。
- 本次不做跨任务的子任务队列。
- 本次不要求每个复杂任务都能调用外部工具完成真实世界动作；无法匹配工具时仍可用 mock 兜底，但步骤状态和清单要准确。

## 任务识别

新增任务类型：

```text
complex_task
```

识别规则：

- LLM 可以直接返回 `complex_task`。
- fallback 识别以下输入特征：
  - 包含“拆解”“分步骤”“一步一步”“步骤”“先…再…最后…”。
  - 包含明显多目标连接词，例如“并且”“同时”“然后”“再”“最后”。
  - 用户明确要求“列出 [1][2][3] 步骤”。

已有专用任务类型优先级更高，例如表格、GEO、代码阅读、历史任务查询仍优先走专用链路。

## 计划拆解

Planner 对 `complex_task` 使用新的拆解逻辑：

- 先尝试从用户输入中提取显式编号步骤：
  - `1.`
  - `1、`
  - `[1]`
  - `（1）`
- 如果没有显式编号，则按中文连接词拆分：
  - “先”
  - “然后”
  - “再”
  - “最后”
  - “并且”
  - “同时”
- 如果仍无法拆分，则生成保守三步：
  - “分析复杂任务目标”
  - “执行主要任务步骤”
  - “汇总复杂任务结果”

步骤数量限制：

- 最少 2 步。
- 最多 8 步。
- 每个步骤去掉空白、编号和多余标点。

## 状态表示

继续使用现有 `PlanStep.status`：

- `pending`
- `running`
- `completed`
- `failed`

新增一个轻量格式化函数，把状态转成 checklist 标记：

```text
pending   -> [ ]
running   -> [...]
completed -> [x]
failed    -> [!]
```

这个格式既用于最终结果，也用于桌面端显示。

## 执行流程

执行流程仍由 `core/loop.py` 控制：

1. `Planner` 创建计划。
2. `plan_created` 事件把步骤发给桌面端。
3. 每步开始时发送 `step_started`。
4. Router 根据步骤目标选择工具。
5. 工具执行后 Verifier 校验。
6. 每步完成时发送 `step_done`。
7. 所有步骤完成后，如果任务类型是 `complex_task`，最终输出生成 checklist 报告。

复杂任务最终输出格式：

```markdown
## 复杂任务执行清单

[x] 1. 第一步任务
[x] 2. 第二步任务
[x] 3. 第三步任务

## 执行结果

已完成 3/3 个步骤。
```

如果失败：

```markdown
## 复杂任务执行清单

[x] 1. 已完成步骤
[!] 2. 失败步骤
[ ] 3. 未执行步骤

## 执行结果

完成 1/3 个步骤，失败 1 个步骤。
```

## 桌面端展示

桌面端 `renderPlan()` 改为显示 checklist 标记：

- 初始计划：`[ ]`
- 正在执行：`[...]`
- 完成：`[x]`
- 失败：`[!]`

当前圆形数字图标改为等宽文本标记，避免用户误解步骤已经完成但图标只是数字。步骤标题和工具名保留。

## 文件影响

预计修改：

- `core/task_parser.py`：允许并识别 `complex_task`。
- `core/planner.py`：增加复杂任务拆解逻辑。
- `core/loop.py`：为复杂任务生成 checklist final output。
- `desktop/frontend/app.js`：步骤 UI 使用 `[ ]/[x]`。
- `desktop/frontend/style.css`：调整步骤标记样式。
- `README.md` / `docs/project-overview.md` / `CHANGELOG.md`：补充说明。
- 测试文件：新增或扩展 parser、planner、loop、frontend 测试。

## 测试

必须覆盖：

- TaskParser 能识别“请分步骤执行…”为 `complex_task`。
- Planner 能从 `[1][2][3]` 拆出多个步骤。
- Planner 能从“先…然后…最后…”拆出多个步骤。
- 复杂任务执行完成后 final output 包含 `[x]` checklist。
- 桌面前端包含 `[ ]/[x]` 状态渲染逻辑。
- 全量测试通过。

## 验收标准

用以下输入测试：

```text
帮我执行一个复杂任务：[1]分析当前项目状态 [2]列出下一步计划 [3]总结风险点
```

预期：

- 任务类型为 `complex_task`。
- 计划至少 3 步。
- 桌面执行过程初始显示 `[ ]`。
- 每步完成后显示 `[x]`。
- 最终结果包含 `## 复杂任务执行清单` 和 3 条 `[x]` 步骤。
