## Context

V1.11 的主体代码已经存在于当前工作区：Planner 能生成结构化步骤，Router 能使用模型选择工具，Loop 能 Replan，桌面端能展示补充信息和计划确认弹窗。自动化测试与 21 条核心评测均通过，但现有实现仍有四个发布风险：成功标准只是被保存而未驱动校验；人工改写步骤会按位置继承旧工具元数据；工具目录只声明默认 action；交互等待对象只存在于进程内存。此次设计在保持现有安全工具层、checkpoint 格式向后兼容和离线规则回退的前提下闭合这些语义。

## Goals / Non-Goals

**Goals:**

- 让步骤成功标准成为可追踪的完成门禁，而不是展示字段。
- 让模型和人工编辑产生的工具选择都受运行时真实契约约束。
- 让等待用户的任务能够跨应用重启恢复，且只消费一次有效决策。
- 保持危险工具逐次授权、工作区边界和确定性文件证据的最高优先级。
- 形成 V1.11 自动化、真实桌面和发布产物三层验收闭环。

**Non-Goals:**

- 不引入多 Agent、任务并行或 DAG 调度。
- 不让模型取代文件系统验证、授权管理器或工作区边界检查。
- 不重做桌面工作台视觉结构，不增加新的业务工具。
- 不要求旧 checkpoint 一次性迁移；读取时按安全默认值补齐新字段。

## Decisions

### 1. 将步骤校验结果建模为独立、可持久化的数据

每个成功标准产生一条结构化结果，至少包含标准文本、是否通过、校验来源、依据和失败原因。Loop 在工具执行后把当前 `PlanStep`、`ToolResult` 与已有文件证据交给 Verifier；只有现有任务级校验和全部必须标准都通过，步骤才能进入 `completed`。

语义型标准可以由模型辅助判断，但结果必须携带实际工具输出依据。目录创建、写入、删除、Shell 影响等高风险结果只能由确定性检查和文件证据确认，模型判断不能覆盖确定性失败。

替代方案是继续只使用任务类型硬编码 Verifier；该方案无法解释模型计划中的每一步为何完成，也不能为 Replan 提供精确标准，因此不采用。

### 2. 工具目录升级为运行时 action 契约，同时保留兼容字段

工具目录为每个已注册工具公开允许的 action、参数 JSON Schema 和 action 级授权要求，并暂时保留 `default_action` 供旧调用方使用。没有显式声明契约的旧工具只暴露其默认 action 和最小对象参数约束。

Planner 生成计划时校验 `tool_hint + action_hint`；Router 执行前再次校验工具、action 和参数。模型输出无效时可进入现有规则回退，但任何未通过契约校验的 action 都不能交给 Executor。

替代方案是在具体工具内部容忍任意 action；这会把模型错误推迟到执行阶段，并使计划确认无法说明真实风险，因此不采用。

### 3. 人工编辑会使受影响步骤的机器绑定失效

保留已完成步骤及其证据；对目标文字发生变化或新增的步骤，清空 `tool_hint`、`action_hint`、`inputs`、`success_criteria` 和旧授权标记，重新编号并只保留有效的前向依赖。执行时由 Router 根据新目标和实时工具目录重新选择。即使用户在计划确认中接受了编辑，高风险 action 仍必须经过工具层单次授权。

替代方案是按位置复用原步骤元数据；这可能让“新目标”执行“旧工具”，因此不采用。

### 4. pending interaction 使用 checkpoint 持久化与可重放事件

在向桌面端发出交互事件前，先把稳定的 `request_id`、类型、问题、计划快照、状态和时间写入 `AgentState.pending_interaction` 并保存 checkpoint。应用恢复任务时，Loop 重新注册同一个 request，重放等待事件并继续使用原 `task_id`。决策写入 `interaction_history` 后清空 pending，再唤醒执行线程。

交互采用“事件可重复、决策只生效一次”的语义：重复回复返回已经处理的状态，不重复推进任务；过期 request 不得作用于其他任务。取消、拒绝或超时均产生明确的非完成状态。

替代方案是恢复时创建全新任务；这会破坏证据、checkpoint 和会话归属，因此不采用。

### 5. 发布门禁分为自动化、真实应用和产物验证

自动化必须覆盖新增契约、旧 checkpoint 兼容、重复回复和安全失败；真实应用覆盖普通聊天、计划编辑、缺少信息、Replan、授权拒绝与跨重启恢复；产物验证覆盖版本一致、`.app` 启动、签名校验、ZIP 完整性和关键资源存在。只有三层全部通过才更新发布状态与标签。

## Risks / Trade-offs

- [自然语言成功标准可能不可客观验证] → 优先使用确定性校验；语义判断必须保存证据和来源，无法判断时失败并触发补充信息或 Replan。
- [工具 action 契约改动影响旧工具] → 保留 `default_action`，为未声明契约的工具生成单 action 兼容契约，并通过现有 773 个测试回归。
- [交互事件重放导致前端重复弹窗] → 前端按 `request_id` 去重，后端决策接口幂等。
- [人工编辑清空绑定增加一次模型路由调用] → 只处理被修改或新增的步骤；安全和正确性优先于一次调用成本。
- [当前工作区包含其他未提交文件] → 实施和发布只纳入本 change 列出的文件，架构可视化临时文件与 review package 不进入版本提交。

## Migration Plan

1. 先扩展 State/checkpoint 的可选字段和兼容读取，确保旧数据可加载。
2. 增加工具 action 契约与双重校验，再切换 Planner/Router 使用新字段。
3. 接入步骤成功标准并保持无标准步骤沿用现有 Verifier 行为。
4. 接入可恢复交互和前端去重，完成进程重启场景测试。
5. 运行全量测试、核心评测和真实桌面验收后重新打包 V1.11。
6. 若发布验收失败，保留旧 checkpoint 兼容代码，回退到 V1.10.6 应用产物；不删除用户数据。

## Open Questions

- 语义成功标准首版是否允许额外模型调用，或仅使用现有 Verifier 与工具证据；实施时以不增加默认调用为优先，无法覆盖的标准明确标为不可判定。
- action 参数契约是否先覆盖 V1.11 实际注册工具，还是一次覆盖全部 vendor 工具；首版以运行时已注册工具为发布边界。
